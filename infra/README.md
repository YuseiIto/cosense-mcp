# Deploying cosense-mcp to AWS

The HTTP transport runs as an arm64 Lambda behind an **API Gateway HTTP API**
under a custom domain. The gateway terminates TLS for that hostname, throttles
before the function runs, and logs every request; **authorization happens in
the application**, which requires a bearer token carrying the `read:cosense`
scope and answers with spec-compliant `WWW-Authenticate` challenges.

Why not the gateway's managed JWT authorizer: its 401s are generated by the
gateway itself, with no `resource_metadata` pointer and a literal `scope=""` —
the former breaks the discovery hop MCP clients start from, the latter risks
steering a client into requesting an empty scope set. HTTP APIs cannot
customize gateway responses, and REST APIs have no managed JWT authorizer at
all. The application's verifier stays, and is tested down to a real RS256
round trip.

Anything under `*.example` is a template. The real files (`backend.hcl`,
`terraform.tfvars`) are gitignored — this repository is public, and those
files name an account, a bucket, a tenant and a hostname.

## Prerequisites

- `cargo-lambda` (bundles Zig) and the `aarch64-unknown-linux-gnu` target
- Terraform >= 1.11
- AWS credentials able to manage Lambda, API Gateway, ACM, IAM, CloudWatch and
  EventBridge
- An existing S3 bucket for Terraform state
- An OAuth 2.0 authorization server that issues RS256 JWTs whose `scope` claim
  reflects what the client was granted. The instructions below use Auth0 with
  RBAC enabled.

## 0. Settle the public hostname first

Everything derives from it: the ACM certificate, the API Gateway custom
domain, `PUBLIC_BASE_URL`, and — critically — the authorization server's API
identifier, which MCP clients receive as the RFC 8707 `resource` parameter.
**On Auth0 that identifier cannot be changed after creation**, so choosing the
hostname late means recreating the API, its permission, its role and the
connector registration.

The rest of this document writes it as `https://mcp.example.com`.

## 1. Configure the authorization server

Create an **API** whose identifier is `https://mcp.example.com/mcp`, with:

- RBAC policy enforcement enabled
- an access token dialect that includes granted scopes in the `scope` claim
- offline access enabled, or clients never receive a refresh token
- a permission named `read:cosense`

Create a **role** holding that permission and assign it to the accounts that
should have access. This assignment is the authorization boundary: anyone able
to sign in gets a valid token, and this server rejects the ones whose `scope`
does not carry the permission. Widening who may sign in — enabling signups on
a connection, say — does not widen who can reach the tools.

Register the MCP client. Claude publishes its metadata at
`https://claude.ai/oauth/mcp-oauth-client-metadata`; read it rather than
transcribing from here. At time of writing it declares callback
`https://claude.ai/api/mcp/auth_callback`, grant types `authorization_code`
and `refresh_token`, and `token_endpoint_auth_method: "none"` — a public
client, so **no client secret is involved**.

**Do not set a default audience on the tenant.** Auth0's resource parameter
compatibility profile only falls back to `resource` when `audience` is absent;
a default audience is equivalent to sending `audience` on every request, and
the token would be minted for the wrong API.

## 2. Build the binary

Run from the repository root. Terraform reads the zip at plan time, so build
first — a clean checkout cannot plan.

```sh
cargo lambda build --release --arm64 --bin lambda --output-format zip
# -> target/lambda/lambda/bootstrap.zip
```

## 3. Configure

```sh
cd infra
cp backend.hcl.example backend.hcl           # state bucket
cp terraform.tfvars.example terraform.tfvars # projects, SID, Auth0, hostname
```

Set `public_base_url` to `https://mcp.example.com` and `auth0_audience` to the
identifier from step 1 — they must agree, minus the path.

Set `aws_account_id`. Credentials for several accounts are often available at
once, and a function created in the wrong one costs nothing and breaks
nothing, so nothing tells you about it.

`discord_webhook_url` is optional and enables the gateway alarms (4xx flood /
any 5xx) delivered to a Discord channel via EventBridge — no code involved.
The URL is a credential: whoever holds it can post to the channel.

## 4. Certificate first, gateway second

The custom domain cannot be created until its certificate is issued, and the
DNS validation record lives in your DNS zone, not here. So:

```sh
terraform init -backend-config=backend.hcl
terraform plan -target=aws_acm_certificate.public -out=tfplan && terraform apply tfplan
terraform output acm_validation_records   # -> create this CNAME in your zone, unproxied
```

ACM deletes certificates that stay unvalidated for **72 hours**, so create the
record promptly, wait for the certificate to reach `ISSUED`
(`aws acm describe-certificate`), then apply the rest:

```sh
terraform plan -out=tfplan && terraform apply tfplan && rm -f tfplan
terraform output api_gateway_regional_domain
```

Plan files contain secrets in plaintext; keep them out of the repository and
delete them straight after.

## 5. Point the hostname at the gateway

Create a CNAME for `mcp.example.com` to the `api_gateway_regional_domain`
output. Proxying it through a CDN works — the gateway holds a certificate for
the real hostname, so Host and SNI stay consistent — but exempt the MCP and
OAuth paths from any bot-management or WAF rules, which are a documented cause
of MCP connection failures.

Verify from a public network:

```sh
curl -sS https://mcp.example.com/health -o /dev/null -w '%{http_code}\n'   # 200
curl -sS https://mcp.example.com/.well-known/oauth-protected-resource/mcp | jq .resource
# -> "https://mcp.example.com/mcp", exactly
curl -sSI -X POST https://mcp.example.com/mcp | grep -i www-authenticate
# -> Bearer realm=..., scope="read:cosense", resource_metadata=...
```

## 6. Register the connector

Add a custom connector for `https://mcp.example.com/mcp` — the path matters,
it must equal the API identifier. Under advanced settings supply the client ID
from step 1 and leave the secret empty.

Sign in with an account that holds the role, and confirm once with an account
that does not: it should authenticate and then be refused.

## Redeploying after code changes

Rebuild (step 2) then `terraform apply`. `code_sha256` changes, so Terraform
updates the function.

## Notes

- **Throttling is the cost bound.** Authorization happens inside the
  application, so every request that reaches the gateway is billed — the stage
  throttles at rate 2/s, burst 10, and `429`s never invoke the function.
  Reserved concurrency is not used because Lambda refuses reservations on
  accounts whose concurrency quota is the minimum of 10.
- **The gateway's default endpoint is disabled.** Only the custom domain
  answers. The `d-xxxx` regional domain remains technically reachable for
  clients that send the right Host header.
- **Access logs** (14 days) record every request including ones the function
  never saw; the `sub` claim is logged, tokens are not.
- For this deployment the authorization server and the DNS zone are declared
  in a separate, private infrastructure repository. Changing who may use this
  server is a change there, not here.
